# SWADEBASE simultaneous multi-user reliability standard — v1.0

**Founder-approved November 19, 2026 (America/Chicago).** Applies to every SWADEBASE-connected site, feature, adapter, AI agent, payment/credit system, voice session, computer session, rendering/media job, webhook, and background worker. Inherited automatically as a policy by all affected Master Site Bibles; a saved standard is not proof existing sites are compliant.

## Non-negotiable behavior
1. **Simultaneous usage:** Never design a feature only for one active person. Users must be able to start, interact with, and finish their own feature requests concurrently without freezing another user's work, confusing sessions or corrupting records. Define expected concurrent-session and active-job capacity before implementation; choose infrastructure accordingly, not by guesswork.
2. **Strict isolation:** Each request, WebSocket/LiveKit room, voice conversation, audio stream, memory/thread, browser/computer lease, uploaded file, wallet, agent selection and long-running job is bound to a server-verified user ID and tenant/site ID. No global `currentUser`, shared mutable active chat, singleton recorder/audio player across users, or shared temporary filenames. Admin delegation/view-as cannot silently grant another person's rights.
3. **Transactional accounting:** Credits, voice minutes, subscriptions, Stripe purchases and refunds, computer-hour consumption, quotas and reservations must be atomic, idempotent and tenant-scoped. Simultaneous authorizations cannot spend the same available balance twice. Admin platform exemptions must derive from trusted identity and remain audited; actual external provider spend retains limits.
4. **Resource scheduling:** Bounded job queues, per-tenant/per-user concurrency ceilings, fair scheduling and backpressure for AI/GPU/render/computer/voice workloads. If full, display a position or retryable capacity status; never claim success, lose a task, silently overspend or let one customer starve others. Live voice receives interactive priority over batch rendering, within owner-approved spend and hardware limits.
5. **Resilience:** Handle network disconnects, Safari backgrounding, retries, agent restarts, two tabs, simultaneous webhook delivery, cancellation and recovery. Resume only the authenticated session; clean up microphone/voice rooms and CPU/GPU leases on hang-up/timeouts. Preserve existing user data and provide rollback; never expose another user's audio or conversation.
6. **Privacy and speech:** Each user has a separate capture stream and explicit microphone permission. Continuous speech-to-speech must have a visible listening/speaking/muted/paused/queued/error state, explicit stop and a user-initiated wake/resume. Background TV and side conversations are difficult to distinguish perfectly; use VAD, echo cancellation, optional local speaker verification and an explicit "ignore me until I resume" state, with no guarantee of perfect rejection. Do not record third parties without consent or silently transcribe if user selected a no-transcription path.
7. **Observability:** Record anonymized counts of active sessions/voice rooms/agent jobs, queue depth, per-tenant errors and p50/p95 turn latency, cost, retries and abandoned sessions without leaking private content. Alerts for queue saturation, cross-tenant access, billing discrepancies and dropped audio.

## Mandatory release gate
- **Before build:** Document workload assumptions (at least expected users/second, simultaneous sessions, long-running jobs, memory, network, CPU/GPU and third-party spend). Provide a per-user/tenant concurrency design, capacity/backpressure method and one rollback.
- **Before deploy:** Pass automated two-user isolation tests and concurrent transaction/idempotency tests. Perform realistic load testing at the declared expected concurrency and a higher stress level, with one voice/browser/payment failure injection where relevant. Examples are 10 / 25 / 50 simultaneous sessions as staged checkpoints, NOT a claim that all sites can already sustain those counts. For real-time voice specifically verify at least two simultaneous independent audio sessions, microphone mute, interruption, session cleanup and no cross-room routing.
- **Acceptance:** Zero cross-user exposure, zero double-credit/charge events, zero lost accepted jobs, no unbounded queues, acceptable p95 latency and error rate defined for the product; retries and session recovery behave as promised. If a checkpoint fails, remain behind a feature flag or scale capacity before launch. Record exact tested user counts, duration, results, limits, provider charges and test date. A single-user success or endpoint HTTP 200 is not a concurrency pass.
- **After deploy:** Monitor real active sessions and customer failure rates; configure bounded autoscaling/queue workers only on approved servers and cost budgets. Alert and fail closed on suspected tenant isolation or payment race issues. Update Master Site Bibles, daily log, SWADEBASE What's New and knowledge index with verified evidence.

## Applying to SWAGENTS first
- Each speaking agent session must keep its own user/agent/thread ID, LiveKit room token, end-of-turn VAD, explicit pause/mute/stop, speaking state and interruption policy; do not share a global mic/recorder or output across visitors.
- Quote and reserve *voice minutes/credits* and agent/computer add-ons server-side per user, reconcile actual consumption. Render separate balances for available voice allowance, wallet credits, number of agents entitled/active and computer hours. Never treat the 10 anonymous preview messages as spendable wallet units.
- Use existing SWADEBASE identity, LiveKit, voice adapters, SWADE Voice Studio and PostgreSQL. Existing SWADE BOTS VAD (3-second silence) is a reference implementation, not proof SWAGENTS has continuous two-way audio. Hyperstack and HARU require separate verified connection/performance review before being chosen.

## Proven versus not-yet-proven
This document is a **new mandatory design/release policy**, not a deployed autoscaling feature, a measured capacity test or a claim that 10/25/50 users currently work. Existing sites require individual audits against this standard, prioritized by active traffic and billing/voice risk.
