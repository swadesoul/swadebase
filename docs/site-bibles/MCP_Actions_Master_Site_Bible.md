## Exact scope
Typed proposals cover a single-file repository repair, exact PR merge, exact-commit Coolify deployment, one email, a GitHub release, owned wiki-draft archival and Stripe connected-account transfers. Source/target lookup and actor-scoped proposal/receipt reads are exposed. Repair creates a draft PR; it does not claim tests passed or a live site was fixed. Deploy acceptance is separate from live workflow verification. Publishing currently means GitHub release publication; deletion currently means reversible owned-draft archival. Arbitrary purchases, bank payouts, permanent data deletion, VPS deletion and arbitrary shell commands are not supported.

## Founder ownership and approval
The existing verified identity source must match swadesoul@gmail.com, confirmed email and current super-admin status. A narrow security-definer boolean function performs that check without granting auth-table reads. Other operators/customer accounts cannot use the founder's execution or payment credentials.

Existing OAuth tokens and legacy tool names are preserved. New scopes are actions:prepare, actions:execute and an additional payments:execute. They require explicit owner consent through reconnection; they are not silently added to existing tokens. The signed-in connection screen offers explicit action and payment options.

The bot can prepare, inspect and execute an approved action. Approval, rejection/revocation, enabling/disabling payment rules and Stripe payer-identity reads use the separate founder session and same-origin/CSRF-protected owner routes. There is no MCP approval or rule-edit tool. Content hashes, actor, expiry, exact target and typed payment confirmation bind the decision. Proposal expiry is thirty minutes; approval expires after ten minutes or the remaining proposal time. A changed request requires fresh review. Unclaimed approvals can be revoked.

## Payment rules
Payments are disabled until the owner explicitly saves enabled rules with source account, live/test mode, currency, named connected-account payees, per-payment and America/Chicago daily transfer-amount caps, and expiry within thirty days. The provider verifies source/mode and transfer-capable payee accounts. Each payment needs its own approval of exact payee, amount, currency, purpose, business reference and current rule digest, plus payments:execute scope at dispatch.

The existing ops_actions store holds policies, approvals, reservations and receipts. Actor locks serialize cap checks and claims. Approved reservations, executing, uncertain and completed transfers consume daily capacity. Payee/reference uniqueness blocks a new request key from bypassing pending/uncertain/completed payments. Unknown provider outcomes cannot automatically retry and remain reserved for reconciliation. Disabling rules blocks new claims; it does not undo already running/submitted transfers. Limits cover transfer principal; provider fees follow existing account terms. No payment was made in tests.

## Data, security and costs
Reuse sssbrain.ops_actions and actor-owned brain_wiki_pages. Add only narrow RLS policies, column grants, indexes and the founder-check function. Transaction-local actor context resets on pool reuse. Private request bodies are not copied to global knowledge. Audit events contain action IDs/digests/outcomes, not credentials or message bodies. Raw MCP bearer tokens never pass upstream.

Provider clients use fixed trusted service endpoints, server-owned target mappings, bounded payloads/timeouts, no automatic write retries and durable claims before dispatch. Known credential patterns and credential paths are withheld from code reads and rejected in action input. The server keeps provider credentials separate from client OAuth. Default registered targets are the verified SSS Brain/SWADEBASE repositories and private ecosystem hub and known SSS Brain Coolify application; additional mappings require verified configuration.

The current runtime has Resend and Stripe credential references, but presence alone is not delivery/payment verification. GitHub and Coolify credential references were absent at inspection. Those handlers return setup-required rather than pretending to repair, publish or deploy. Do not copy the ChatGPT GitHub connection's authorization into model-visible text. Use a protected service connection and appropriate least-privilege credentials.

The cost/usage Studio reuses the existing adapter registry, AI ledger and rate cards. Ledger totals are recorded usage only; empty/unpriced/uninstrumented data is not zero cost. Payments have their own operation/provider receipts and are not misclassified as AI inference cost. No paid API/model, email, release, website deployment or user draft mutation was invoked by the synthetic tests.
